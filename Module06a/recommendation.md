# Decision memo to Lea Winter and Yasmin Kaya

Move the two full-history reporting aggregates to a reproducible Parquet copy, while keeping operational writes and point lookups in SQLite. On this machine, the dashboard median fell from 5,832.15 ms in SQLite to 74.13 ms in DuckDB (78.67× faster), with equivalent 350-row results. The monthly report fell from 7,013.05 ms to 74.27 ms (94.43× faster), with equivalent 1,500-row results. The original Task 2 Parquet was 2,323,412 bytes and its Zstandard copy was 1,367,276 bytes; the later direct-history refresh produced 2,468,865 and 1,447,194 bytes with the same logical data. Run `refresh.py` nightly after the last shift so it builds a temporary file from `history.db`, validates it, and atomically publishes only a passing snapshot. Its `--check` detects differences in row count, price and ID sums, date limits, nulls, and schema, but matching summaries cannot prove that every individual field is identical. If refresh fails or becomes stale, keep the last validated file, alert the report owner, and label reports with the snapshot timestamp; do not move request-per-row work because 1,000 DuckDB inserts and lookups took 6,549.83 ms and 2,710.14 ms versus SQLite's 3.30 ms and 4.33 ms.
